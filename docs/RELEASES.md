# Version and release policy

Versions use `X.y.z`:

- `X` changes only after the user explicitly authorizes that exact major change. Never infer permission from a feature request, milestone, breaking change, or request to prepare release automation.
- `y` increases for new features or systems, retaining `X` and resetting `z` to zero.
- `z` increases for corrections to existing behavior, retaining `X.y`.

This development pass is **0.6.0**, following 0.5.0. No major change is authorized, and it does not produce automated release packages. Keep `VERSION` and the `project(... VERSION ...)` value in `CMakeLists.txt` identical. Local `build.sh linux`, `build.sh windows`, and `build.sh all` remain available at every version.

## Major release procedure

1. Obtain explicit user permission to advance `X`; record the authorized version in the release notes. The workflow cannot determine conversational authorization, so maintainers must enforce this policy before tagging or publishing.
2. Update both version locations to the authorized `X.0.0` and commit the tested source and workflow. Review both Windows and Linux build requirements.
3. Create an immutable tag `vX.0.0` at that reviewed commit, where `X >= 1`. Publish a stable GitHub Release for that tag using a human account or an authorized token that triggers release events. Events generated by the repository's `GITHUB_TOKEN` ordinarily do not trigger another workflow.
4. The published release starts `.github/workflows/major-release.yml`. It validates the exact tag/version match and checks all other published stable release versions: the new `X` must exceed every previous stable major. Releases must retain their history; deleting historical releases defeats that history check.
5. Both native build jobs must build and pass CTest before packages are attached. Linux also runs the OpenGL smoke renderer. Both installed packages run the headless executable with the source data directory moved aside to verify packaged data discovery.
6. Download the two release assets and verify their hashes against `SHA256SUMS.txt`. Extract the entire archive before launching the desktop executable.

There are no push, pull request, manual dispatch, feature, patch, or 0.x package build triggers. `release: published` also fires for prereleases, so the first job explicitly skips drafts and prereleases. Non-major stable tags are skipped before the build jobs. The workflow never changes a version, creates a tag, or creates a release.

## Packages and recovery

- `escalation-vX.0.0-windows-x86_64.zip`: native Windows x64 executables built with Visual Studio 2022 and the static C/C++ runtime. Requires a working OpenGL 3.3 graphics driver.
- `escalation-vX.0.0-linux-x86_64.tar.gz`: native Ubuntu 24.04 x64 executables. Requires glibc 2.39 or newer, X11 desktop libraries (`libx11-6`, `libxrandr2`, `libxinerama1`, `libxcursor1`, `libxi6`) and an OpenGL 3.3 graphics driver. This is a native archive, not a universal Linux runtime bundle.

Both include the desktop and headless executables, data, fonts, README, notices, and third-party licenses through CMake's existing install rules. Linux tar preserves executable permissions. Windows uses a zip archive.

Only the final attachment job receives `contents: write`; checkout and build jobs have read access. Actions are pinned to verified full commit SHAs. Archive artifacts are retained for seven days, and both platforms are collected before the final upload. Uploads never use `--clobber` and reject releases with existing assets. The workflow's per-tag concurrency group serializes runs.

A failed build with no assets can be retried using GitHub's existing run retry controls. Do not delete and republish old releases or move released tags to force a build. A partially failed asset upload requires inspection and deliberate recovery by a maintainer; the workflow will refuse an automatic replacement. GitHub asset uploads are not transactional. Immutable release settings can prevent post-publication attachment; this workflow requires release assets to remain writable until its attachment step completes.
